The problem

  • Millions of log lines don't fit in a prompt.
  • An agent can explain a failure — but it needs focused evidence, not raw logs.
  • Three people ask about the same logs and need different evidence and decisions:

Engineer

What failed, where, and what happened just before & after?

Team Lead

What recurs, how often, which teams own it?

Manager

What to prioritise first — and why?

Any

Every answer must cite the query that produced it.

2The problem

The approach — the database does the work

  • SereneDB searches (BM25 full-text) and aggregates (counts, trends, latency) before anything reaches the agent.
  • The agent picks parameterised tools — no open-ended SQL.
  • Every number is checkable: each tool returns the SQL, filters, data scope, row count and a truncation flag.
  • Facts vs. hypotheses kept separate; the manager view uses measured frequency only — no invented impact.
question → [agent picks a tool] → SereneDB query → evidence → role-specific answer

6Team Lead · the key insight

Manager — prioritise by spread + ownership

  • 1. Kernel Platform, long-running: KERNMC (144d) + KERNRTSP (126d) + KERNMNTF (26d) → kernel-oncall.
  • 2. Application Runtime: APPSEV — 49,651 lines, 70 days, 1,024 distinct nodes → apprt-oncall.
  • 3. OpenStack nova-api — 2,068 error-keyword lines (2.01%) → API Gateway.
  • 4. Bursts as retrospectives: KERNDTLB (99.6% on 2005-06-12); KERNSTOR peaks the same day as KERNRTSP's burst.
  • 5. Monitor only: nova-compute (0.20%), nova-scheduler (0 of 866).

Honest framing: BGL uses the dataset's labels; OpenStack "error" = ERROR/CRITICAL level or error keywords, not labelled anomalies. Ranked within each dataset — counts are matching log lines, not confirmed incidents. No invented downtime / cost / customer impact.

8Rigor & reproducibility

It scales — and we state the limits

  • Optional award: 1,000,000,000 rows of remote OpenTelemetry Parquet, queried in place, zero download (read_parquet over S3).
  • COUNT(*) 0.1s · GROUP BY service ~15s · GROUP BY severity ~12s.
  • Honest limit: aggregation over remote Parquet scales freely; a full-text index on 1B rows needs more RAM than 6 GiB.
